# Clarify

## 核心目标

把用户真正表达的意图变成一条语义等价、边界清晰、可直接交给 AI 执行的指令。

把“澄清”与“扩展需求”严格分开。保留用户的目标、动作、对象、限定词、否定项、优先级和语气强度；不得替用户增加新目标、交付物、技术方案、流程门禁或质量标准。

## 调用模式

- **显式调用**：用户通过 `$clarify`、技能入口或自然语言明确要求澄清、完善、优化、重构或精炼指令。默认终点是**优化后的指令**，不执行下游任务；只有用户明确要求“澄清后继续执行”时才继续。
- **自动调用**：任务中出现实质歧义、指代不明、约束冲突、关键上下文缺失或动作权限不清时，将本技能作为前置检查。若意图和动作边界已足够明确，不展示改写过程，直接继续原任务；若存在阻塞性歧义，仅暂停依赖该答案的动作，简述阻塞点及影响并向用户确认；继续不依赖答案的已授权工作。不要仅因收到任务指令就触发，也不要把正常任务都改写后退回给用户。

两种模式都保留原意和权限边界。显式重写使用完整语义清单与双向语义审计；自动调用只检查影响当前动作的歧义，不输出完整改写或要求重新审批已明确的任务。

## 不可违反的原则

1. **原意优先**：准确理解高于表达美化。
2. **证据优先**：先使用当前消息、对话上下文和所处环境消解歧义，再向用户提问。
3. **最小补全**：只补足能从上下文确定的信息；不能确定的内容保持未指定或提问确认。
4. **关键歧义才提问**：只有不同答案会明显改变目标、范围、交付物、动作权限、外部影响或执行方式时，才阻塞并询问。
5. **最少问题**：优先询问信息增益最高的一个问题；能合并为一个明确选择时不要拆成问卷。
6. **不静默猜测**：存在阻塞性未决项时说明具体分歧，不把推断伪装成用户要求。自动调用只询问必要问题；显式重写保留带待确认项的完整语义复述。未收到回答、超时或预选项均不构成答案或审批。
7. **保持语义强度**：不得把“必须”弱化为“建议”，不得把“尽量”强化为“必须”，不得丢失“只、不要、除非、优先、至少、至多”等限定词。
8. **不制造执行权限**：不得把“分析/解释/审阅”重写成“修改/创建/发送/部署”。

## 工作流

### 1. 建立语义清单

从原指令和可靠上下文中提取：

- 核心目标：用户最终想得到什么
- 动作：解释、查找、分析、比较、设计、修改、创建、执行或其他
- 对象与范围：针对什么，包含和排除什么
- 交付物：回答、方案、代码、文件、表格、图、命令等
- 约束：技术、时间、格式、兼容性、资源、权限和禁止项
- 成功标准：怎样算完成
- 上下文：已有文件、代码库、环境、先前决策和用户已提供的信息
- 未决项：原文没有说明且上下文不能确定的内容

不要为了填满清单而虚构字段。用户未指定且不影响任务正确性的内容可以继续保持未指定。

### 2. 根据上下文消歧

按以下优先级寻找证据：

1. 当前消息中的显式陈述
2. 当前对话中仍然有效的决定、约束和指代
3. 用户明确提供或要求使用的文件、代码库、日志和运行环境
4. 与任务直接相关、可安全读取的现状信息

仅在现状信息能够直接解决歧义时进行只读检查。不要把澄清变成无边界调研，也不要为了提出“更专业”的问题而主动扩展任务。

### 3. 判定是否需要提问

把未决项分为三类：

- **阻塞性歧义**：不同解释会产生显著不同的目标、范围、外部影响或不可逆结果。必须提问。
- **可安全保留的未指定项**：可以在优化后的指令中保持开放，不必提问。
- **可由上下文唯一确定**：直接补入，并确保有明确证据。

不要把每个缺失的执行细节都升级为阻塞性歧义。只有必须由用户作出、且无法在执行过程中从上下文或实际环境确定的决定才阻塞；措辞、通知内容、常规实现细节等可以保持未指定。

用反事实测试判断是否阻塞：

> 如果选择另一种合理解释，最终交付物或执行动作会明显不同吗？

若答案为“否”，不要打断用户。

采用最小权限解释动作边界：

- “查看、解释、分析、审阅、评估”等只读动作默认不包含修改、创建、发送或部署权限，不要询问用户是否顺便扩大权限。
- “修改、创建、发送、部署”等动作已经明确授权相应操作，不要退回成只读分析。
- “处理、搞定、解决”等词若结合上下文仍无法确定是只读诊断还是直接变更，才将动作权限列为阻塞性歧义。

### 4. 提出最小澄清问题

需要提问时：

- 自动调用：简述阻塞点、已有上下文和不同答案的影响，不要求复核整条任务。
- 显式重写：给出完整理解，保留目标、动作、范围和禁止项，标出待确认部分。
- 少量彼此独立且必要的问题可以一次提出；存在答案依赖时按顺序询问。
- 只列真实分支，可用 2–3 个互斥选项解释影响；不借机扩展目标或权限。
- 不重复询问已回答或可从当前上下文、环境确定的信息。
- 用户询问问题背景时，解释后保持原问题待答；不能把等待结束当作授权。
- 暂停依赖该答案的动作，同时继续其余已授权工作；全部工作都依赖答案时明确说明。

### 5. 重写指令

使用原指令的语言，除非用户要求翻译。按任务需要组织为以下顺序：

1. 角色或任务定位（仅当原文已有或确有助于消除歧义）
2. 核心目标
3. 输入与上下文
4. 要执行的动作
5. 范围与约束
6. 输出要求
7. 完成标准
8. 禁止项或非目标

使用明确动词、稳定指代和可验证表述。可以删除不承载意图的重复和空泛修饰，但不要删除承载意图的重复强调。发现互相冲突的约束时，必须先依据可靠上下文消解；若无法消解，将冲突双方完整保留并列为阻塞性待确认项，不得自行删除、弱化或选择其中一方。

不要自动加入以下常见“AI 套话”，除非原意要求：

- “遵循最佳实践”
- “生产级”
- “全面考虑所有情况”
- “提供多个方案”
- “必须先制定计划并等待批准”
- “使用某个特定框架、工具或模型”

### 6. 做双向语义审计

输出前逐项检查：

- **原文 → 新指令**：原文每个重要信息是否都被保留？
- **新指令 → 原文**：新指令中的每个要求是否都能追溯到原文或可靠上下文？
- 是否改变了动作权限、范围、优先级、语气强度或否定条件？
- 是否把建议写成了要求，把假设写成了事实？
- 是否仍存在会导致不同结果的代词、模糊量词或冲突约束？
- 优化后的指令是否无需读取本次解释就能独立使用？

若双向审计不通过，继续修订，不要输出。

## 输出约定

### 尚需澄清

自动调用只输出必要问题及其影响。显式重写使用以下结构：

```markdown
## 当前理解的完整指令

<完整列出已经确定的指令；将所有阻塞性未决项标为“待确认：……”>

## 请确认

<询问必要待确认项；独立问题可合并，依赖问题按顺序处理>
```

可以在问题后附一行说明“为什么这个选择会改变结果”。这里的“完整指令”是带有显式待确认项的完整语义复述，不得提前选择分支，也不得生成一个把猜测当成事实的最终指令。

### 已可重写

默认使用：

```markdown
## 优化后的指令

<可独立使用的完整指令>
```

仅当有必要帮助用户核对语义时，追加：

```markdown
## 保留与处理说明

- 保留：<容易在重写中丢失的关键限定>
- 保持未指定：<不应由 AI 擅自决定的非阻塞项>
```

不要展示冗长的内部分析过程。不要声称“补全”了用户没有表达的需求。
